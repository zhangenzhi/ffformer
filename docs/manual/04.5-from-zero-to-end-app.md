# 4.5 From Zero to End App ― 从一个想法,到 dashboard 一步步长成

> **本章目的**:带你走一遍 **JPeaks-Forest 仪表盘**的"孕育过程"——它不是一次设计好的,而是从一个很朴素的想法出发,撞上一个个真实问题,和 Claude Code 一轮轮把它一步步养大的。读完你会明白:每一块功能**为什么**存在。

## 0. 起点:一个很朴素的想法

我们手里有两样东西:一堆森林的无人机/LiDAR 点云,和一个能把点云里**每棵树分割出来**的模型(ForestFormer3D)。问题是——这个模型跑在**超算**上,要 SSH 登录、写 PBS 作业脚本、命令行操作。对做森林的研究者来说,这门槛太高了。

于是有了最初的一句话愿望:

> **"能不能给它做个网页?研究者把点云拖进去,就能看到每棵树的分割结果和分析,完全不用碰超算。"**

整个项目就是从这句话长出来的。

---

## 1. 第一个岔路口:前台和后端必须分家

刚要动手就撞到一个现实约束:

- **研究云**(Kubernetes,能开网页给人访问)——但**几乎没有 GPU**。
- **超算**(有成排的 GPU)——但**没有对外的网页入口**,只能内部 SSH。

两边各有一半,谁都不能单独把事办了。所以第一个、也是最重要的设计决定诞生了:

> **薄前台 + 重后端**:网页(前台)放在研究云,只管交互;真正吃 GPU 的分割和 LLM 放在超算(后端);中间用 **SSH + PBS 投作业**把两边接起来。

```mermaid
flowchart LR
    U([用户浏览器])

    subgraph RC["研究云 · Kubernetes"]
        FE["薄前台<br/>网页 / 交互<br/>✅ 有对外网页入口<br/>❌ 几乎没有 GPU"]
    end

    subgraph HPC["超算 · HPC"]
        BE["重后端<br/>分割 + LLM<br/>✅ 成排的 GPU<br/>❌ 无对外网页入口"]
    end

    U -->|"① HTTPS 打开网页"| FE
    FE -->|"② SSH + PBS 投作业"| BE
    BE -->|"③ 结果回传"| FE
```

> 看图就懂"各有一半":研究云有**入口**没 **GPU**,超算有 **GPU** 没**入口**;`SSH + PBS` 这座桥把两半接成一个能用的整体。

这条"两层架构"定了调,后面所有东西都长在它上面。第一次跟 Claude Code 说的,其实就是这个骨架:

```
做一个网页服务(FastAPI):用户上传点云后,
通过 SSH 把一个分割任务投到超算(PBS 队列),
等它跑完,把结果下载回来展示。前端先来个单页 dashboard.html。
```

> **为什么前端选"单页 + 内联"**:研究云上部署越简单越好,不想再养一套前端构建。所以整个前端就一个 `dashboard.html`,CSS/JS 全内联,烤进镜像即走。这个选择很省事,但也埋了个雷(见第 6 节)。

## 2. 验证整条计算链路

这一步暂时不开发正式功能,而是先验证上一节设计的计算链路能否真正跑通:

> 将点云从研究云传到超算,在超算上提交 GPU 分割任务,等待任务完成,再把结果文件取回。

验证时,我们不通过网页逐项手动操作,而是让 Claude Code 编写一组小型测试脚本,并使用一份真实但规模较小的点云数据,自动走完整条链路。

这样做的目的,是把原本依赖人工操作的验证过程,变成一套**可以重复执行、能够明确判断成功或失败的测试**。

### 按链路逐步生成测试

我们按照数据流转顺序,把任务逐步描述给 Claude Code:

> **① 上传测试数据**
> 将一小份测试点云上传到超算指定目录,并检查文件是否存在、大小是否正确。
>
> **② 提交计算任务**
> 通过 SSH 登录超算的登录节点,调用 `qsub` 提交点云分割任务,并打印返回的作业号。
>
> **③ 等待任务完成**
> 根据作业号轮询队列状态,每隔几秒输出一次进度;任务结束后,检查超算侧是否生成了 `result.ply`。
>
> **④ 取回并验证结果**
> 将 `result.ply` 下载到研究云或本地验证环境,检查文件是否存在,并核对点数、文件大小等基本信息。
>
> **⑤ 串联端到端流程**
> 将上传、提交、等待和下载四个步骤组合成一个完整测试。任何一步失败,都必须指出失败阶段并输出原始错误信息。
>
> **⑥ 根据报错迭代修复**
> 当测试失败时,直接把完整报错交给 Claude Code,例如:
> "运行时出现以下错误:`<粘贴原始报错>`。请解释原因,修改对应测试,并重新运行。"

Claude Code 会把这些要求分别落实为测试文件,执行测试,并根据输出继续修改。经过几轮迭代后,整条计算链路就不再只是架构图上的连线,而是变成了一组实际运行过的自动化测试。

### 为什么每一步都要写成独立测试

这里有一个重要原则:**每个环节都应保存为独立的测试文件,而不是只执行一次临时命令。**

独立测试具有明确的输入、输出和通过条件,因此 Claude Code 可以自行运行测试、查看结果并判断是否成功,不需要人工持续观察和解释。

与此同时,这些文件还会沉淀为后续可复用的诊断工具。例如:

* SSH 是否可用;
* 输入文件能否上传;
* PBS 作业能否提交;
* 队列状态能否查询;
* 推理结果是否生成;
* 结果文件能否下载。

以后无论是修改环境、迁移集群,还是排查线上问题,都可以直接重新运行相应测试,而不必从头手动检查。

### 最终得到的测试集

| 测试文件 | 验证动作 | 通过标准 |
| --- | --- | --- |
| `test_upload.py` | 将测试点云上传到超算 | 文件存在,路径和大小正确 |
| `test_ssh.py` | SSH 登录超算并执行 `qstat` | 能正常连接,并读取队列信息 |
| `test_submit.py` | 使用 `qsub` 提交分割任务 | 返回有效作业号,任务进入排队或运行状态 |
| `test_infer.py` | 等待作业结束并检查输出 | 任务正常完成,生成 `result.ply` |
| `test_fetch.py` | 将 `result.ply` 下载回来 | 文件成功到达,点数或文件大小符合预期 |
| `test_pipeline.py` | 串联完整端到端流程 | 上传、提交、GPU 分割、下载和结果校验全部通过 |

> 表中的文件名只是示例,应替换为项目中实际保留下来的测试文件名。

### 用测试结果完成排障闭环

排障时,不需要重新检查整条链路。先运行各环节的独立测试,定位具体失败位置,再把该测试的原始报错交给 Claude Code。

例如:

* `test_ssh.py` 失败,通常应检查 SSH 密钥、主机地址或来源网段;
* `test_submit.py` 失败,可能与 PBS 队列、用户组或资源参数有关;
* `test_infer.py` 失败,应检查运行环境、模型路径和 GPU 日志;
* `test_fetch.py` 失败,则重点检查输出路径、文件权限和传输命令。

Claude Code 根据报错修改对应测试,再重新执行。最终,当 `test_pipeline.py` 能够从上传输入数据开始,一直运行到结果下载和校验全部通过时,就可以确认:

> **研究云与超算之间的端到端计算链路已经实际验通。**

## 3. 做出第一个可用 Demo:把跑通的链路接进网页

上一节,我们用一组测试脚本证明了整条计算链路确实能够跑通。但测试脚本只能证明系统"能工作",还不能让普通用户真正使用它。

这一节先不追求完整产品,而是搭一个**最小可用的 Demo 网页应用**:把已经验证过的上传、提交、等待和取回结果流程封装进后端,再接到一个可以点击操作的界面上。

目标很明确:让用户不用再碰命令行,也能在浏览器里完整走一遍"导入点云 → 提交分割 → 查看进度 → 打开结果"的流程。

> **严格说,不是把链路封装成网页,而是**:先把链路逻辑封装成后端模块,再通过接口接到网页上。所以第二、三节之间不是"重做一遍",而是一次明确的**重构与封装**;上一节的测试也不丢,稍作调整继续当回归。

### 分三层,各管一件事

应用分成三层:

* **超算接入层 `hpc_backend.py`**:负责和超算通信,包括 SSH 连接、文件上传、`qsub` 提交、作业状态查询和结果取回。
* **接口层 `server.py`(FastAPI)**:把超算接入层的能力包装成 HTTP 接口,并管理数据编号、任务编号和错误信息。
* **界面层 `dashboard.html`**:提供 Import、Segment 和 Analyze 三个页签,调用接口并展示任务进度和计算结果。

只要接口约定不变,各层就可以独立调整:修改网页样式不需要接触 SSH 逻辑;更换超算地址或传输方式,也不需要改动前端。

```mermaid
flowchart LR
    U([用户浏览器])
    subgraph FE["界面层 · dashboard.html(单页)"]
        T["Import · Segment · Analyze"]
    end
    subgraph API["接口层 · server.py(FastAPI)"]
        E["/import · /segment/{id}<br/>/task/{id}/status · /result/{id}"]
    end
    subgraph BK["超算接入层 · hpc_backend.py"]
        H["SSH · qsub · 轮询 · 下载"]
    end
    HPC[(超算)]
    U --> T --> E --> H
    H -->|"SSH + PBS"| HPC
```

### 从验证脚本到应用函数(对应关系)

上一节留下的不只是一批临时脚本,更是一套**可执行规格**:每个脚本都定义了一个环节怎样才算通过。这一节按照这些规格实现应用代码,再让测试继续守住这些行为。所以这里是**对应关系**,不是"脚本升级成代码"——一张表对齐每个环节:

| 链路步骤 | 上一节的验证脚本 | `hpc_backend.py` 中的函数 | `server.py` 对外接口 |
| --- | --- | --- | --- |
| 上传 | `test_upload.py` | `upload_input()` | `POST /import` |
| 提交 | `test_submit.py` | `submit_job(dataset_id)` | `POST /segment/{dataset_id}` |
| 查询 | `test_infer.py` | `get_job_status(task_id)` | `GET /task/{task_id}/status` |
| 下载 | `test_fetch.py` | `fetch_result(task_id)` | `GET /result/{task_id}` |

> `/import` 成功后返回 `dataset_id`,用于标识这份输入数据;提交分割后返回 `task_id`,用于查询作业状态和获取结果。这样前端不需要知道 PBS 作业号、超算目录等底层细节。

> 换句话说:测试文件不是生产代码的上一个形态,而是它的**可执行验收标准**——先写出明确的通过条件,再让 Claude Code 实现、运行和修正。

### 和 Claude Code 一步步搭

> **①** 后端·超算接入层:把已经验证过的 SSH、上传、提交、轮询和下载流程,抽取到 `hpc_backend.py` 中。不要复制整段测试代码,而是整理成可复用函数。
>
> **②** 后端·回归验证:修改上一节的测试,让它们调用 `hpc_backend.py` 中的新函数;重新执行,确保重构前后行为一致。
>
> **③** 后端·接口层:用 FastAPI 在 `server.py` 中提供 `/import`、`/segment/{dataset_id}`、`/task/{task_id}/status` 和 `/result/{task_id}` 接口。为这些接口编写自动化测试。
>
> **④** 前端·页面骨架:创建单页 `dashboard.html`,包含 Import、Segment 和 Analyze 三个页签,CSS 和 JavaScript 暂时全部内联。
>
> **⑤** 前端·接通流程:Import 上传文件并获得 `dataset_id`;Segment 提交任务并获得 `task_id`;页面定时查询任务状态,任务完成后加载结果。
>
> **⑥** 端到端验证:用浏览器自动化脚本完整执行一次"上传 → 提交 → 等待 → 展示结果"。功能流程由测试判断是否通过,页面布局再通过人工查看确认。

这样就和上一节形成了统一的方法:**先写出明确的通过条件,再让 Claude Code 实现、运行和修正。**

> **结果落在哪里**:脚本验证阶段,结果被拉回测试机器;进入网页应用后,结果首先被 `hpc_backend.py` 取回到**研究云上的应用目录**,再由 FastAPI 提供给浏览器——超算生成 `result.ply` → 取回研究云 → FastAPI 把结果或预览给浏览器。**浏览器本身不直接连接超算。**

> **设计回看:为什么暂时坚持单页内联**
> 第一节选择"单页 + 内联 CSS/JS",使初版部署非常简单:一个 `dashboard.html` 就能随镜像发布。但这种做法也会让前端代码随功能增加而变脆弱,第 6 节会专门处理这个问题。

### 结果:应用链路跑通了,新的瓶颈出现在浏览器

到这里,用户已经可以在网页上完成上传、提交任务、查看进度和打开结果,功能链路算是跑通了。

但把完整的 `result.ply` 交给浏览器后,一个新问题很快暴露出来:**后端能够生成和传回结果,不代表浏览器能够一次性流畅显示它。**

在本项目的数据规模下,一个结果文件可能包含数千万甚至上亿个点。浏览器如果一次性下载、解析并绘制全部点,页面就会明显卡顿。

最直接的临时方案,是先做**降采样**:把点云按比例抽稀到浏览器扛得住的点数,再渲染出来。

> 结果点云太大,网页渲染很卡。先做个降采样:把点数抽稀到大约 X 万个再画,让用户能快速看到一个整体概览。

这样很快就有了一版能看的初步界面:

![初版 UI:降采样后的分割预览界面](img/initial-ui.png)

*初版仪表盘:三页签(Import / Segment / Analyze)+ 左侧降采样后的实例分割预览(每棵树一种颜色)+ 右侧运行面板。此图为示意 mockup。*

> **三条链路**:第二节验证了**计算链路**,这一节打通了**应用链路**;但要真正处理大规模点云,还需要解决**可视化链路**——这正是下一节流式查看器要处理的问题。

## 4. 让浏览器扛住上亿个点:流式查看器

上一节用全局降采样先把显示顶住了,但那只是权宜之计。

### 降采样的天花板

全局降采样——把整片云抽稀到固定点数——有两个躲不掉的问题:抽得狠,放大看某棵树就糊、结构也丢;抽得轻,面对几 GB、上亿点的结果,浏览器还是扛不住。根子在于:它对"你现在在看哪、要多细"**一无所知**,只能一刀切。

### 关键思路:不整包,按需、由粗到细

解决办法是借用在线地图的思路。看地图时,缩得很小只加载一张粗略概览;放大到某个城市,才加载那一块的精细瓦片,而不是把全国的高清地图一次性下载下来。

点云也可以这样组织,用的数据结构叫**八叉树(octree)**:

* 把整个点云所在的空间切成一个大立方体,再递归地把每个立方体切成 8 个小立方体,一层比一层细;
* 每个节点只保存一份**子采样**(抽稀)后的点。越靠近根部越粗略,越往下越精细。

查看器据此工作:先加载最粗的根节点,**立刻**给出一张概览;然后根据相机的视角和距离,**只拉当前看得见、且需要那个精度的瓦片**,边看边补细节。这样无论原始点云多大,浏览器任一时刻都只持有很小一部分。

### 和 Claude Code 一步步做出来

同样按数据流转顺序,分步描述给 Claude Code,每步都能单独验证:

> **① 后端:预处理成八叉树**
> 把结果 PLY 组织成八叉树,导出一份元数据 `metadata.json`(描述有哪些节点、各自的范围和层级)和每个节点一份瓦片文件 `tiles/*.bin`(存该节点的子采样点)。
>
> **② 前端:先出概览**
> 用 Three.js 建一个点云场景,读 `metadata.json`,先加载根节点,让用户立刻看到一张粗略全景。
>
> **③ 按视野补细节**
> 相机移动或放大时,根据视角和距离计算该加载哪些更细的瓦片,逐步拉取、逐步变清晰。
>
> **④ 上色与交互**
> 支持按语义(树 / 地面 / …)或按实例(每棵树不同颜色)上色,并能调节点的大小。
>
> **⑤ 用真实大结果验证**
> 拿一个几 GB 的真实结果打开:确认几秒内出概览、拖动流畅、内存不爆。

### 沉淀的原则

> **Stream, don't dump(流式,别整包甩)**:大数据不要整包发给客户端,而是后端预处理成分层瓦片,前端只拉看得见的那部分。

这条原则不止用在查看器上——后面第 7 节讲媒体库时还会再遇到它。

## 5. 撞墙 ②:跑一次好几分钟,用户对着空白页干等

分割一片大林子要好几分钟。第一版是"点了按钮,然后……啥也没有,等着"。没人受得了。

于是长出了**实时反馈**这一层:

- 前端**轮询** `/task/{id}/status`,画**进度条**;
- 更进一步:分割是**分块(tiled)**跑的,所以**每完成一个瓦片就先渲染出来**——用户能眼看着林子一块块"长"出来,而不是盯着空白。

> **经验**:凡是"要等"的地方,都得让用户**看见它在动**。后来这条又催生了"查看器拉取时的加载指示"这类打磨(第 9 节)。

## 6. 撞墙 ③:一个撇号,整页 JS 全废

随着功能变多,"单页 + 内联 JS"的雷踩响了:有一次改 `dashboard.html` 里的内联脚本,不小心在字符串里多了个撇号,**整段 JS 直接挂掉,整个页面白屏**。

教训变成了一条铁律:

> **改完内联 JS,必须 `node --check`**(把内联脚本抽出来做语法检查)再提交。

这不是"单页内联"这个选择错了——它依旧让部署极简;只是它有代价,而代价要用纪律来管。

---

## 7. 长出血肉:登录、媒体库、分析报告

主干稳了,开始往丰满走。每一块还是同样的节奏——**描述需求 → Claude 改 → 本机看 → 不对再说**:

- **登录 / 多用户**:不能谁都能进,于是加了账号系统,未登录只显示登录卡。
- **媒体库(结果持久化)**:这里又撞了一次墙——前台 pod 的 `/tmp` **一重启就清空**,历史结果全没了。但结果其实**一直在超算上**。于是做了"媒体库":列表从超算**重建**,点开时才按需把该结果的八叉树拉回来(又是 *stream, don't dump*)。
- **LLM / VLM 分析**:光有分割不够,研究者还想要**物种、健康、碳**。于是加了 Analyze 页:整片林子的**场景分析**(stand-level)、点单棵树的**健康分析**(per-tree),这些同样投到超算的 GPU 上跑大模型。

---

## 8. 还有一条暗线:大文件传得慢

前台后端分处两地,大点云要在它们之间来回传。可这条链路一度只有 **~1 Gbps**(走的是超算的管理网口),传个几 GB 就得等半天。这背后是一整条网络排查(公网 IP、rclone、方向选择),目前仍在优化——它不改变 app 的样子,但决定了它**用起来爽不爽**。

> 这条线告诉你:一个真实系统的瓶颈,常常不在你最初盯着的地方(模型),而在**周边**(网络、存储、重启)。

---

## 9. 怎么让它"每天都能改":快速迭代循环

功能越加越多,就越需要**改起来快**。这里有个关键机制:镜像里的 `/app` 是个 git 仓库、**启动时会 `git pull`**。于是改前端**根本不用重打那个巨大的镜像**:

```
改 dashboard.html / server.py  →  node --check(内联 JS 改过就查)
   →  git push origin main  →  kubectl rollout restart(新 pod 自动拉最新代码)
```

几十秒,新版就上线了。正是这个循环,让 dashboard 能像本章描述的这样"一轮一轮"快速长大。细节和回滚见 [10](10-更新とトラブル対処.md)。

本手册写作期间,它还在继续长——比如:任务不再硬超时、加了手动取消;查看器拉取时加了转圈+计时;把品牌统一成 **JPeaks-Forest**……每一条都是"发现一个不爽 → 一轮改掉"。

---

## 10. 回头看:它是怎么长成现在这样的

把成长线连起来,其实就几条一以贯之的原则在起作用:

| 撞到的问题 | 长出的东西 | 沉淀的原则 |
|---|---|---|
| 模型只能在超算命令行跑 | 两层架构(薄前台+重后端) | 各用所长,SSH/PBS 搭桥 |
| 结果几 GB,浏览器卡死 | 八叉树流式查看器 | **Stream, don't dump** |
| 跑一次好几分钟 | 进度条 + 增量瓦片预览 | 要等就让人看见在动 |
| 内联 JS 一个撇号全废 | `node --check` 纪律 | 简单的选择,用纪律兜底 |
| pod 重启结果就没 | 媒体库从超算重建 | 状态放在可靠的一侧(超算) |
| 大文件传得慢 | 网络链路优化(进行中) | 瓶颈常在周边,不在核心 |
| 功能越加越多要常改 | git-pull + rollout restart | 让迭代循环短到几十秒 |

> 这就是它从**一句"能不能做个网页"**,一步步长成今天这个 dashboard 的过程。
